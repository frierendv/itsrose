Each package becomes a ~40-line adapter supplying its own Zod schemas and error map. Six adapters behind one concept — the seam is real, not hypothetical.

Problem

Six packages independently re-decide how to build a client, how to attach credentials, how to translate an upstream error, and how to shape a response. Nothing learned in one package transfers to another, and the Zod schema each package exports as its interface is never actually enforced.

The dashboard already guesses: status === "paid" || status === "settlement". That guess is the leak, visible in the UI.

Problem

One status column carries three merged vendor vocabularies. A single transient gateway read failure turns a paid invoice into status: "settlement", which silently skips the subscription settlement, defeats the idempotency guard, and makes the invoice voidable — because "settlement" is absent from NON_VOIDABLE_STATUSES.

Solution

The adapter normalises vendor status into a domain InvoiceStatus union, using the isSuccessStatus helper @itsrose/midtrans already ships. The domain asks “is this paid?” once, in one place.

Wins

  • the money path stops depending on a literal
  • idempotency guard recognises paid invoices again
  • dashboard deletes its compensation branch
  • 4 transaction statuses currently classified by no predicate
  • one status vocabulary per module, not three

Deletion test

Delete the normalisation and the "paid" literal reappears in every caller — complexity concentrates behind the seam. Deep.

Top recommendation

Candidate 03 — one invoice-status vocabulary

It is the only candidate where the architecture can cost money. A single transient gateway read failure writes status: "settlement" into a paid invoice, and the settlement gate — a literal comparison against "paid" — silently skips the subscription. The idempotency guard stops recognising the invoice, and isVoidableStatus makes it voidable because "settlement" is not in the non-voidable list. The dashboard already carries its own compensation (status === "paid" || status === "settlement"), which means the leak has already reached the UI.

It is also the cheapest of the strong candidates: normalise in the adapter, where the project’s own rules already permit vendor knowledge, and reuse the isSuccessStatus helper @itsrose/midtrans already ships and nobody calls. The change removes a literal rather than adding machinery, and it is the prerequisite for the midtrans findings (the signature amount-format invariant and the duplicated error model) landing on a coherent footing.

Jump to Candidate 03 · C5 is the cheapest by hours · C1 is the biggest locality win
